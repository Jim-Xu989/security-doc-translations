## 项目牵头人来信

不要试图去构建一个无法被欺骗的模型。要在模型周围构建系统，这样当模型被欺骗时——它迟早会被骗——重要的东西不会崩溃。这种姿态贯穿了这里列出的全部十条。今年，我们第一次能够向你展示证据，而不是要求你凭信心接受。

在此之前的每个版本，都是建立在判断之上的。数百名从业者对哪些问题最为重要表达了意见。那次投票仍然是这份清单的支柱，而且它理应如此。今年，我们做了一件这个项目从未做过的事。我们用一份真实出错的记录来检验这次投票。我们从公开的漏洞数据库和一个 AI 危害数据库中汇集了 7,714 起真实事件的语料库，并构建了分类器来阅读它们，对其中 6,639 起包含足够细节、可以归类的事件进行了分类。然后我们提出了一个直白的问题：从业者所担忧的，与事件记录所显示的，是否一致？

答案是否定的——至少并非总是如此，而这正是令人意外之处。投票与数据在特定而有用的地方分道扬镳，而那些分歧比共识教会了我们更多。

提示注入是最清晰的例子。从业者将其列为头号风险。但如果按原始事件记录对各类别排序，它会跌出前十名之外。这一差距是一种防御效应。各团队全力对抗注入攻击，因此进入公开数据库的干净漏洞利用更少，而公开计数低估了成熟团队已经在真金白银投入防御的风险。攻击面仍然存在于模型读取不受信任输入的每一处，也就是说，无处不在。它仍居第一位。既然你无法关闭这个攻击面，你就要为它被用来对付你的那一天做好准备。

错误信息则走向另一个方向，我想请你在此放慢脚步。投票者将它排在接近末尾的位置。事件记录则将它排在接近顶端的位置，这是方向上落差最大的一处——投票偏低而证据偏高，恰恰是会造成实际伤害的方向。清单仍将"错误信息"置于中段：投票占据更大的权重，但证据将它向上拉动。分歧正是关键所在。当模型那流畅而自信的输出驱动了一个决策或一次工具调用时，一个错误的答案就会变成一次错误的行动，而记录表明，这种失败发生得比投票所假设的更频繁。

社区投票占据四分之三的权重。事件数据覆盖剩下的四分之一。我们有意对投票赋予了较重的权重。这份清单是共识的产物，而一年嘈杂的数据不足以推翻一线从业者的判断。当信念与证据之间的差距很大时，四分之一的权重足以让某个条目移动一个层级。但它还不足以让不完美的数据自行改写这份清单。正是这种平衡决定了 Top 10 中的每一个最终席位。

若干条目也有所扩展。我们将更新的、更尖锐的风险，并入了本已涵盖它们的条目之中。凭空设立单薄的新类别只会徒劳地分裂清单。提示注入如今涵盖跨模态攻击，即那种将指令隐藏在图像或音轨中的攻击。供应链如今涵盖了当被推广的模型产物名不副实时所出现的信任失败。数据与模型投毒如今吸收了微调颠覆。不当输出处理如今涵盖了智能体大规模生成的不安全代码。这些风险背后的事件向来都是真实的。如今它们在理应归属之处被计入。

有一条边界逐年变得更为重要。当模型是你应用中的一个组件时，这份清单负责该风险。一旦该模型成为一个行动者，配有它可调用的工具、跨会话携带的记忆，以及它在下游引发的后果，风险就转移到了 OWASP 智能体式 Top 10。我们阅读的许多事件恰好就处在这条边界上。在此阅读某个条目，可了解模型即组件的失败情形。当你的模型开始自行行动时，请将它与智能体式清单配合使用，因为单凭任何一方都无法覆盖这块领域。

## LLM01:2026 提示注入

### 描述

提示注入漏洞出现在以下情况中：当输入到大语言模型（LLM）的内容——无论是直接的用户输入、检索到的内容、工具输出、图像、音频或视频内容、中间推理过程，还是持久化记忆——以应用开发者不期望的方式改变了模型的行为。LLM在架构上并不区分"指令"和"数据"（两者都是同一数据流上的令牌），因此不存在等价于参数化查询的干净方案（NCSC, 2025）。输入无需是人类可读的，无需直接来自用户，也无需在渲染后的界面中可见即可影响模型。

提示注入漏洞存在于模型如何处理输入，以及该输入如何能够迫使模型将数据或指令错误地传递给系统其他部分的方式之中。三个部署期特性使这一问题更加严重。第一，上下文窗口池化（context-window pooling）：模型将系统提示、用户输入、检索到的文档、工具输出、对话历史和记忆视为单一的令牌流，没有强制实施的信任边界。第二，记忆持久化：写入长期记忆、RAG语料库、向量库或托管记忆服务的注入，会污染此后从该存储读取的每一次会话。第三，智能体式执行（agentic execution）：当模型的输出驱动工具调用（文件系统、shell、电子邮件、云API、MCP服务器、子智能体）时，影响半径（爆炸半径）从聊天面扩展到该智能体工具所能触及的任何地方，并且工具输出会重新进入上下文窗口，从而产生链式或自我复制的效应。

提示注入的构成可以从三个维度来描述。投递面（Delivery surface）指它如何抵达模型（直接输入、检索内容、工具输出、工具连接通道，或持久化记忆）。传播行为（Propagation behavior）指它如何在时间与边界之间扩散（单次攻击、多步杀伤链、通过记忆或RAG的跨会话，或在智能体间自我复制）。编码（Encoding）指恶意指令如何在令牌或像素中表示（纯文本、base64或其他混淆、不可见Unicode、多模态或隐写术、低资源语言）。在选定适用缓解措施之前，沿这些维度拆解一个场景是行之有效的威胁建模步骤。

一次成功的提示注入的严重程度与性质，随模型所处的业务上下文以及为其设计的代理权限而异。提示注入可能导致的结果包括但不限于：

- 泄露敏感信息、系统提示（系统提示词）内容、检索到的私有文档，或基础设施细节。
- 操纵模型输出，产生下游系统或用户据以行动的、带有偏见、有害或攻击者选定的内容。

- 未经授权地调用该智能体被允许调用的工具，在智能体拥有shell、文件系统或云API访问权限的情况下，升级为任意命令执行和破坏性操作。
- 通过图像URL通道、渲染输出中的隐藏Unicode字符，或隐蔽的工具日志侧信道进行数据外泄（外带）。
- 通过记忆或RAG语料投毒，跨会话持久性地破坏智能体行为。

注：提示注入不同于LLM02:2026 敏感信息泄露（Sensitive Information Disclosure），后者处理模型通过其输出泄露的内容（包括推理通道内容）；也不同于LLM03:2026 过度代理（过度能动性）（Excessive Agency），后者处理模型输出抵达特权操作所带来的后果。本条目关注的是输入边界本身。在模型输出抵达下游组件之前对其进行清理与校验，由LLM10:2026 不当输出处理（Improper Output Handling）涵盖。

### 提示注入的类型

#### 直接提示注入

用户，或拥有用户访问路径的攻击者，提供以不良方式改变模型行为的输入。直接注入可能出于故意（恶意用户精心构造越狱），也可能出于无意（合法用户粘贴的内容恰好包含相互冲突的指令，或用户依赖LLM帮助自己，并不经意地针对某个无关的下游LLM优化了其输入，如场景 #3所述）。

越狱（Jailbreaking）是提示注入的一个子集，其攻击者的目标是使模型违反其安全协议。应用级保障措施有助于遏制它，但有效的预防需要对模型的训练与安全机制持续更新。

#### 间接提示注入

模型从外部来源（网页、文档、电子邮件、工具响应、检索到的RAG片段、图像、MCP服务器的输出、数据库行，或问题标题）摄取包含充当提示注入的数据的内容。用户并没有提供或看到这些指令。投递面的信任画像决定了哪些防御是可行的：

- 不可信面（Untrusted surfaces）。公共网页、来自未知发件人的电子邮件、搜索结果。防御者必须将这些来源的任何内容视为可疑。大多数提示注入研究都集中在此处。
- 半可信面（Semi-trusted surfaces）。公共缺陷追踪器中的问题标题、软件包README与变更日志、第三方API响应：用户选择检索但未创作的内容。用户信任平台，但不一定信任个别贡献者。

- 可信面（Trusted surfaces）。开发者自己的仓库、数据库、内部文档和邮件。开发者可能未意识到攻击者已通过某个无关的上游向量（例如公共缺陷报告表单）将内容放置于此。

共同的结构：攻击者无需直接攻陷后端。他们将文本放置在开发者的LLM将会读取的位置，而该LLM以开发者的权限运行，替攻击者完成了工作。只关注聊天面的防御会完全遗漏这一点。

间接提示注入正越来越多地将用户自己的LLM实例变成针对用户自己后端的武器。其模式是：攻击者通过低权限通道（公共表单、客户工单、社区拉取请求）向一个被用户信任的位置提交文本，并等待用户那连接MCP的智能体或开发者助手在用户的提升凭据下读取该文本。执行特权操作的，是智能体而非攻击者（见常见示例 #3；场景 #9逐步演示了生产环境的验证概念）。

### 常见风险示例

1. 直接提示输入覆盖：用户消息覆盖了系统提示的角色与能力限制，使模型在其预期范围之外进行泄露、生成或行动。故意与无意的输入都算在内。
2. 通过检索内容的间接注入：攻击者指令搭乘RAG片段、网页、文档或电子邮件，并在内容抵达上下文窗口时执行（例如EmailGPT；INCIBE-CERT, 2024）。
3. 可信面间接注入：植入低权限但受信任通道（问题追踪器、反馈表单、支持工单）的文本，使用户自己的LLM在其自身的提升凭据下行动，外泄仓库、转储数据库或修改IDE配置——这些是攻击者无法直接执行的操作（Invariant Labs, 2025; General Analysis, 2025; Rehberger, 2025a）。
4. 多模态与隐写术注入：图像、音频或视频中的亚感知扰动被编码器提取（Clusmann et al., 2025；见场景 #6）。

### 预防与缓解策略

提示注入是当前生成式AI固有的：LLM在架构上不区分指令与数据，且其行为是随机的，因此当今不存在可靠的预防机制，这一立场与NIST (2025)、NCSC (2025) 以及Debenedetti et al. (2025) 一致。因此，防御是架构性的而非拦截性的。在周围系统的设计中，应明确假设模型的指令边界最终会被绕过，并限制模型被允许执行的操作，以及其输出被允许触及的范围，从而使一次成功的注入不会转化为一次成功的利用。

有记录以来大多数高影响的提示注入事件之所以变得严重，是因为注入落在了这样一个系统中：其中的工具、作用域或输出渲染能力让被攻陷的模型得以在用户的权限级别上代表攻击者行动（见场景 #7至#9）。这就是本条目与LLM03:2026 过度代理（过度能动性）（Excessive Agency）之间的运维关系：提示注入是输入侧的失陷，而过度的功能、权限或自主性，则是让该失陷在聊天窗口之外产生后果的原因。Simon Willison的"致命三要素"（lethal trifecta，2025）将同一结构性诊断重述为一项部署前检查：一个能够同时访问私有数据、摄取不可信内容并与外部通信的智能体，具备了高影响利用的条件，而移除任意一条腿即可消除这些条件。

将下述控制措施作为纵深防御（defense-in-depth）来应用，因为没有任何单一控制是充分的。其中一些能降低注入成功率，但预计会在自适应攻击者面前退化。另一些则在注入成功后限制影响半径（爆炸半径），这些才是能够抵御能够探测系统的攻击者的措施。对于智能体式部署，最小权限与能力预算控制（#4、#8）是承重结构，而LLM03:2026承载了完整的代理侧论述。

1. 在系统提示中约束模型的角色与能力。使用声明式的允许与拒绝语句（"仅协助X，不要访问Y，不要将输出转发至外部地址"），而非开放式授权。这只是一个部分性控制：推断出提示的攻击者可以绕过它（Nasr et al., 2025），因此需与#4中的权限控制配合使用。

2. 定义严格的输出模式（schema），并在任何下游系统据以行动之前，在可信的应用代码中校验每一条响应，使用结构校验而非第二次LLM调用。这能捕捉格式违规，而非语义操纵：一个模式有效的响应仍可能夹带恶意的SQL查询或外泄格式的电子邮件正文。

8. 以"双规"（Rule of Two）作为下限来预算智能体能力（Meta AI, 2025）。将同时访问（A）不可信输入、（B）敏感数据、（C）状态变更或外部通信视为高风险：任何[A,B,C]智能体都需要逐操作的人工审批，而[A,B]或[A,C]配置需要明确的残余风险评估（见场景 #8）。NIST AI 100-2 E2025以及CISA、FBI、NSA和ACSC的OT指南（CISA et al., 2025）认可该规则，但它对自主性深度保持沉默（Noma Security, 2025）。
9. 将智能体记忆写入视为特权操作。记录引发该写入的提示，对写入内容就指令或角色修改进行分类，并在承载指令的记忆跨会话持久化之前要求审批。2025年2月的一个Gemini验证概念（Rehberger, 2025b）通过延迟工具调用投毒了记忆（MITRE, n.d.）。事实性条目会渐变为指令，而增量写入可规避逐次写入的分类。

## LLM02:2026 敏感信息泄露

### 描述

敏感信息泄露发生在集成 LLM 的系统通过数据主体、控制者或系统所有者未授权的渠道，暴露机密、受监管、特权或专有数据时。该渠道不仅仅是最终答案：工具调用参数、推理轨迹、检索到的片段、多模态输出、日志、遥测数据、嵌入（向量）以及可观测的推理属性（时序、token 长度、对数概率、置信度、缓存命中行为）都是泄露面。应将每一处都视为输出，并适用相同的分类与脱敏规则。

泄露出现在 LLM 生命周期的四个阶段：

1. 训练时。模型、微调模型或 LoRA 适配器记忆语料内容，并在之后以逐字或可以恢复的形式复现它。记忆能力随容量、重复率和上下文长度呈对数线性增长。窄适配器以高保真度记忆罕见示例，这是一个有别于基础模型的有针对性提取面。
2. 推理时。模型泄露实时上下文（系统提示、RAG 片段、文件、工具输出、记忆或另一会话的数据），往往是因为摘要、翻译或提取所暴露的内容超出了所请求的范围，包括视觉上已被删除的内容片段。
3. 管道时。微调、蒸馏、合成数据生成、梯度、SDK 以及可观测性将敏感数据移入派生产物中。
4. 观测时。攻击者在未接收到内容的情况下，从外部可测量的属性（TLS 下的 token 长度、延迟、对数概率、置信度、缓存命中信号）推断出事实。

受保护的信息包括 PII、PHI、财务数据、凭证、API 密钥、商业秘密、模型权重、特权通信、机密或出口管制材料，以及生物特征和基因组标识符。

两处结构性缺陷导致了大多数事件。第一，上游过度共享：未限定范围的驱动器、遗留权限和知识库向 RAG 提供敏感数据，模型随后按设计检索这些数据。修复对象是数据面，而非模型（DSGAI01）。第二，持久性：一旦数据影响了权重、嵌入（向量）或适配器，在源数据删除后它仍可被提取，从而加重 GDPR 第 17 条和 CCPA §1798.105 的删除义务。开放权重的部署无法依赖速率限制，因为提取、成员推断和逆向在离线状态下以无限制速率运行。

6. 训练管道泄露。恶意服务器的梯度逆向（Boenisch et al., 2021）、蒸馏和合成数据残留将示例移入派生模型。针对受 DP 保护模型的迭代查询攻击会优化 LLM 生成的查询，并锁定置信度峰值以重新识别个人，因此固定 epsilon 的 DP 是必要的但尚不充分，还需速率限制、查询模式检测以及每用户预算。
7. 平台与生态泄露。可观测性平台（Langfuse、LangSmith、Datadog LLM Observability）默认记录完整的提示、补全、片段和轨迹。两起代表性事件：DeepSeek 于 2025 年 1 月的 ClickHouse 暴露了超过一百万行日志和 API 密钥（Wiz, 2025）；以及 Check Point 于 2026 年披露的通过代码执行运行时中一个隐藏的外联通道进行的 ChatGPT 数据外泄，其中一个精心构造的提示在可见答案保持无害的同时，将该运行时变成了静默的 DNS 通道（Check Point Research, 2026）。

### 预防与缓解策略

缓解措施遵循 DSGAI 的分层结构，以提供循序渐进的实施路径。

#### Tier 1：基础层（每次部署）

1. 治理语料：跨近似重复项、音译和格式变体的来源、分类与去重。在摄入时清除 PII。去重可减少但不能消除记忆。
2. 最小化上下文：仅向外部提供方发送任务所需的字段。除非按模板确有理由，否则禁用自动上下文（customer_360、全记录追加）。
3. 检索前先授权：在索引查询内部而非检索后的应用层，强制执行文档级与片段级授权。对高敏感工作负载隔离每租户索引。
4. 系统提示卫生：绝不在系统提示中存储密钥、凭证或受监管数据。
5. 用分类器而非仅靠正则进行净化：模式匹配加 NER 加训练出的分类器，因为正则在编码与跨语言输出上会失效。
6. 对敏感端点的每用户与每会话查询设定预算，以阻断枚举与成员探查。
7. 运维卫生：在纳入 APM 之前限制并清除日志与轨迹，传输与静态加密，并以技术手段强制执行 no-train/no-retain（不训练/不保留），而非仅靠策略文本。

#### Tier 2：加固层（受监管 / 高敏感）

1. 校准至敏感度与基数的 DP-SGD，并将过拟合作为记忆的代理指标进行监控。与检测配合，因为固定预算在自适应查询下会退化。

2. 向量库（向量存储）保护：加密、独立于文档 ACL（访问控制列表）的 ACL、受限制的导出 API、最小范围 k-NN，以及嵌入（向量）空间探查检测。

6. 对结构化标识符采用保形加密，配合严格的内部与外部路由分离，以及在外部路径上采用字段允许列表。
7. 将 AI 感知的审计日志接入 SIEM、持续的 DLP 与 AI-SPM，以及带有强制连接策略的、已文档化的域清单，使各自被允许的来源无法组合成被禁止的结论。

#### Tier 3：高级层（受监管、机密、高价值目标）

1. 机密计算（Intel TDX、AMD SEV-SNP、AWS Nitro Enclaves）或新兴的隐私保护推理（AloePri 协变混淆框架，Lin et al., 2026），在威胁模型证明其效用与延迟成本的合理性时使用。
2. 跨原始数据、嵌入（向量）、检查点和适配器的可验证删除，通过后取消学习提取与成员推断探针进行验证。
3. 将泄露红队测试作为发布关卡：提取、成员推断、嵌入（向量）逆向、内部状态逆向、侧信道以及 LoRA 可提取性，进行量化度量并与 MITRE ATLAS 对齐。
4. 针对提取器审计合成数据。通过探查检测、速率限制与水印抵御蒸馏。对聚合分析设定预算。
5. 演练泄露事件响应预案：按数据类别与受影响主体或会话界定范围，然后评估并履行适用的泄露与严重事件通知义务，跨相关框架（例如 GDPR、HIPAA 与 EU AI Act 第 73 条）。随后执行取消学习、再训练或撤回、向量与缓存清理、厂商通知以及持久内存审计。

## LLM03:2026 过度代理（过度能动性）

### 描述

基于 LLM 的系统通常被其开发者赋予一定程度的代理能力（能动性）：即能够调用函数或通过工具（不同厂商也称为扩展、插件或技能）与其他系统交互，以响应提示而采取行动。LLM 智能体还可以根据输入提示或先前的 LLM 输出，动态地选择要调用哪个工具。基于智能体的系统通常会反复调用 LLM，利用先前调用的输出来支撑并引导后续调用。

过度代理（过度能动性）是一种漏洞，它使得系统能够响应 LLM 意外、模糊或被操纵的输出而执行具有破坏性的操作，无论导致 LLM 故障的原因是什么。常见触发因素包括：

- 由工程不佳的良性提示导致的幻觉/虚构，或仅仅是一个表现不佳/未对齐的模型，
- 来自恶意用户的直接/间接提示注入，来自早期被调用的恶意/被攻陷工具，或（在多智能体/协作系统中）来自恶意/被攻陷的对等智能体。

过度代理（过度能动性）的根本原因通常是一个或多个：

- 过度的功能，
- 过度的权限，
- 过度的自主性。

过度代理（过度能动性）可能导致保密性、完整性和可用性各个维度上广泛的影响，并取决于基于 LLM 的应用能够与哪些系统进行交互。在智能体式系统的背景下，过度代理（过度能动性）可表现为 ASI02：工具滥用与利用、ASI03：身份与权限滥用以及 ASI08：级联故障。

注：过度代理（过度能动性）不同于不当输出处理，后者关注的是对 LLM 输出审查不足。对模型输入和输出的净化并非针对过度代理（过度能动性）的根本控制手段，相关输入问题由 LLM01:2026 提示注入覆盖，输出问题由 LLM10:2026 不当输出处理覆盖。

### 常见风险示例

1. 过度的功能

LLM 智能体可以访问的工具中包含系统预期运行所不需要的函数。例如，开发者需要赋予某个 LLM 智能体从代码仓库读取文档的能力，但他们选择使用的第三方工具还包含修改和删除文档的能力。

2. 过度的功能

某个工具可能在开发阶段试用过，后来被更好的替代方案取代而弃用，但原始工具仍然可供 LLM 智能体使用。

3. 过度的功能

一个具有开放式功能的 LLM 工具未能正确过滤输入指令中超出应用预期运行所必需范围的命令。例如，一个用于运行某个特定 shell 命令的工具未能正确阻止执行其他 shell 命令。

4. 过度的权限

LLM 工具在下游系统上拥有的权限超出了应用预期运行的需要。例如，一个旨在读取数据的工具使用某个身份连接到数据库服务器，该身份不仅拥有 SELECT 权限，还拥有 UPDATE、INSERT 和 DELETE 权限。

5. 过度的权限

一个设计用于在单个用户上下文中执行操作的 LLM 工具，却使用一个通用的高权限身份访问下游系统。例如，一个用于读取当前用户文档存储的工具，却使用一个拥有访问所有用户文件权限的特权账户连接到文档存储库。

6. 过度的自主性

基于 LLM 的应用或工具未能独立核实并批准高影响操作。例如，一个允许用户文档被删除的工具在未获得用户任何确认的情况下执行删除操作。

### 预防与缓解策略

以下措施可以预防过度代理（过度能动性）：

1. 最小化工具

将允许 LLM 智能体调用的工具限制为仅最小必要。例如，如果基于 LLM 的系统不需要获取 URL 内容的能力，那么就不应该向 LLM 智能体提供此类工具。

<!-- 原书第 25 页 -->

2. 最小化工具功能

将 LLM 工具中实现的函数限制为最小必要。例如，一个用于访问用户邮箱以汇总邮件的工具可能只需要读取邮件的能力，因此该工具不应包含删除或发送消息等其他功能。

3. 避免开放式工具

尽可能避免使用开放式工具（例如，运行 shell 命令、获取 URL 等），而应使用功能更细粒度的工具。例如，基于 LLM 的应用可能需要将某些输出写入文件。如果这是通过使用运行 shell 函数的工具来实现的，那么产生不良操作的范围就会非常大（可以执行任何其他 shell 命令）。一个更安全的替代方案是构建一个只实现该特定功能的专用文件写入工具。工具应为任何输入参数定义严格的模式（schema），并在使用前校验其内容。

4. 最小化工具权限

将授予 LLM 工具对其他系统的权限限制为最小必要，以缩小不良操作的范围。例如，一个使用产品数据库向客户推荐购买产品的 LLM 智能体可能只需要对"products"表的读取访问权限。它不应访问其他表，也不应具备插入、更新或删除记录的能力。这应通过为 LLM 工具用于连接数据库的身份应用适当的数据库权限来强制执行。

5. 在用户上下文中执行工具

跟踪用户授权和安全作用域，确保代表用户执行的操作是在该特定用户的上下文中、以最小必要权限在下游系统上执行的。例如，一个读取用户代码仓库的 LLM 工具应要求用户通过 OAuth 进行身份验证，并使用最小必要的范围。在委托式或多智能体工作流中，应在链式工具或智能体调用之间保留原始用户上下文和授权范围，而不是仅依赖调用智能体或服务身份的权限。

6. 要求用户批准

使用"人在回路"控制，要求由人工在采取高影响操作前进行批准。这可以实施在下游系统（LLM 应用范围之外）中，或实施在 LLM 工具本身内部。例如，一个代表用户在社交媒体上创建并发布内容的基于 LLM 的应用，应在实现"发布"操作的工具中包含用户批准例程。

7. 完全中介

在逻辑中实现授权，而不是依赖 LLM 来决定某个操作是否被允许。强制执行完全中介原则，使所有对下游系统的请求都由工具、由工具与下游系统之间的独立执行前策略决策点，或由下游系统本身根据安全策略进行验证。此类策略有助于管理以下情况：

### 示例攻击场景

#### 场景 #1：被劫持的电子邮件助手

一个基于 LLM 的个人助手应用通过某个工具被授予访问个人邮箱的能力，以汇总 incoming 邮件的内容。为实现此功能，该工具需要读取消息的能力，但系统开发者选择使用的工具还包含发送消息的函数。该应用还容易受到间接提示注入攻击，即一封精心构造的恶意 incoming 邮件诱使 LLM 命令智能体扫描用户的收件箱以寻找敏感信息，并将其转发到攻击者的电子邮件地址。这可以通过以下方式避免：

- 通过使用仅实现邮件读取能力的工具来消除过度的功能，
- 通过经由具有只读范围的 OAuth 会话向用户的电子邮件服务进行身份验证来消除过度的权限，和/或
- 通过要求用户手动审查并点击 LLM 工具起草的每封邮件的"发送"来消除过度的自主性。

或者，可以通过在邮件发送接口上实施速率限制来减少所造成的损害。

## LLM04:2026 供应链

### 描述

LLM 供应链容易受到影响训练数据、模型、适配器、转换流水线和部署平台完整性的漏洞的影响，从而导致有偏见的输出、安全漏洞或系统故障。虽然传统的软件漏洞侧重于代码缺陷和依赖项，但在机器学习中，风险扩展到第三方预训练模型、数据集和模型制品（artifacts），这些都可能通过篡改、投毒或恶意制品替换而被操纵。

创建 LLM 是一项专业工作，依赖于第三方模型、数据集，以及使用参数高效微调（PEFT）技术（如 LoRA（低秩自适应））构建并在 Hugging Face 等平台上共享的可复用适配器。供应链现在将模型制品、来源（provenance）以及转换/合并工作流作为一等攻击面，而设备端 LLM 进一步扩大了这一范围。

此处涵盖的部分风险也在 LLM05:2026 数据与模型投毒中进行了讨论。本条目侧重于其供应链方面。特定于智能体式应用的供应链风险，包括 MCP 服务器和工具注册表，由 OWASP 智能体式应用十大（OWASP GenAI Security Project, 2026）中的 ASI04 智能体式供应链漏洞覆盖，而 MITRE ATLAS 在 AML.T0010 AI 供应链攻陷（MITRE, n.d.）下编录了相应的对手技术。

### 常见风险示例

1. 脆弱或过时的第三方组件与模型

过时或已弃用的组件（包括包、服务框架以及模型本身）可能被利用以攻陷 LLM 应用。这与 A06:2021 脆弱与过时组件类似，但当组件在模型开发、微调或推理期间使用时，风险会增加。LLM 编程助手增加了一种新变体：它们大规模地幻觉出看似合理但不存在的包名（Spracklen et al., 2025），攻击者会提前注册这些包名（"slopsquatting"），使得未经验证的 AI 建议依赖项解析到恶意代码。

2. 许可风险

AI 开发涉及多样的软件和数据集许可，这些许可施加了不同的使用、分发和商业化要求。如果管理不当，它们会造成法律和合规风险敞口。

<!-- 原书第 29 页 -->

3. 脆弱或被篡改的预训练模型

模型制品难以被全面审查，仅靠静态分析无法确定行为安全性。预训练模型可能包含通过投毒数据集或直接篡改引入的隐藏偏见或后门。远离诸如 Python pickle 之类不安全的序列化格式（它可以在加载时执行任意代码）可以降低但不能消除此风险：后门可以直接嵌入模型的计算图中，并在被广泛认为安全的格式（如 ONNX）中持续存在，而精心构造的模型文件可以利用某格式原生解析器中的内存破坏漏洞，正如 llama.cpp 的 GGUF 解析中的堆溢出（CVE-2024-23496）（Cisco Talos, 2024）所示。

4. 弱来源与未签名的模型制品

已发布的模型不提供强有力的来源保证：模型卡（Model Cards）记录了一个模型，但无法证明其来源，而一个被攻陷或冒名顶替的供应商账户可以以受信任的名称发布恶意模型。当模型、适配器、数据集、微调检查点以及转换输出未被签名或哈希固定（hash-pinned）时，攻击者可以在传输中、存储中，或在自动化流水线将制品接纳到受信任环境的提升（promotion）边界处替换或静默更改制品，特别是当流水线通过可变引用（例如 latest 标签）而非不可变摘要来解析制品时。

5. 脆弱的适配器以及被攻陷的转换、合并与量化工作流

LoRA 适配器使微调变得模块化和高效，但恶意适配器可能破坏预训练基础模型的完整性，无论是在协作式模型合并环境中，还是在下载并对已部署模型应用适配器的推理平台上。模型转换和合并服务可以在格式之间的转换过程中引入恶意更改，绕过审查控制。量化是一种相关的转换风险：可以精心构造模型权重，使得全精度模型评估为良性，而量化后的制品表现出攻击者选择的行为（Egashira et al., 2025），因此全精度的保证不会转移到已部署的量化制品上。

6. 设备端 LLM 供应链漏洞

随设备提供的 LLM 将受攻陷的制造流程、对设备操作系统或固件漏洞的利用，以及带有被篡改模型的重新打包应用加入到攻击面中，使设备完整性和固件信任成为 LLM 供应链的一部分。

7. 不清晰的条款与条件（T&Cs）及数据隐私政策

模型运营商不清晰的条款与条件（T&Cs）和数据隐私政策可能导致敏感应用数据被用于模型训练并随后被暴露，并可能产生由模型供应商提供的材料带来的版权风险。

### 预防与缓解策略

1. 仔细审查数据源和供应商，包括 T&Cs 和隐私政策，并且只使用受信任的供应商。定期审查和审计供应商的安全性及访问权限，并在其安全态势或 T&Cs 发生变化时重新评估。

2. 应用 OWASP 十大中的 A06:2021 脆弱与过时组件的缓解措施：漏洞扫描、管理，以及使应用保持在受维护的组件、API 和底层模型版本上的修补策略。对可访问敏感数据的开发环境应用相同的控制，并在采用 AI 建议的依赖项之前，验证其确实存在且为预期的包。

3. 在选择第三方模型时应用 AI 红队测试和评估，聚焦于范围内的用例，并在生产环境中通过 MLOps 和 LLM 流水线中的异常检测和对抗鲁棒性测试持续进行，以检测篡改和投毒。

4. 使用软件物料清单（SBOM）维护一份最新的、已签名的组件清单，并扩展至模型、适配器和数据集，采用 AI 物料清单（AIBOMs）和 ML SBOM，评估诸如 OWASP CycloneDX ML-BOM（OWASP CycloneDX, n.d.）和 OWASP AIBOM 项目（OWASP GenAI Security Project, 2025）等选项。在同一清单中跟踪许可，并定期审计以确保合规和透明。

5. 仅使用来自可验证来源的模型，并通过第三方完整性检查、签名和文件哈希来弥补弱来源。由透明日志（例如 OpenSSF Model Signing 项目和 Sigstore）支持的加密模型签名将模型制品绑定到签名者身份（Open Source Security Foundation, 2025）。模型训练无法保证可复现构建，而安全 AI 联盟（CoSAI）提供了一个用于签名 ML 制品的成熟度模型（OASIS Open, 2025）。签名证明完整性和来源，而非安全性（来自被攻陷或受信任但恶意的供应商的有效签名模型仍可能被植入后门），因此应将其与不可变制品引用、来源策略、基于策略的发布门禁（例如 SLSA）（Open Source Security Foundation, n.d.）、行为评估以及对上游模型完整性的持续验证相结合。类似地，对外部提供的代码使用代码签名。

6. 严格监控和审计协作式模型开发环境，并将模型转换和合并服务视为高风险的提升点。

7. 对部署在边缘的模型进行加密并配合完整性检查，使用供应商证明（attestation）API 来防止被篡改的应用和模型，并拒绝无法识别的固件和不受信任的设备状态。

### 示例攻击场景

#### 场景 #1：被攻陷的包与服务框架

一个被攻陷的依赖项进入模型开发或推理环境，正如 2022 年 12 月的 PyTorch 供应链攻击，其中 PyPI 注册表上一个恶意的 torchtriton 包遮蔽了合法的 PyTorch-nightly 依赖项并外泄数据（PyTorch Foundation, 2022）。服务栈是同一攻击面的一部分：ShadowRay 攻击在野利用了存在争议的 CVE-2023-48022（生产环境 Ray 服务器上未经验证的仪表盘），后来升级为跨暴露集群的自我传播僵尸网络（Lumelsky & Elbaz, 2025），而在 Ollama 中，CVE-2024-37032 允许通过从注册表拉取的恶意模型清单实现远程代码执行（Wiz, 2024）。

#### 场景 #2：发布到中心的被篡改模型

攻击者以看似受信任的名称发布一个被篡改的模型，正如 PoisonGPT 概念验证所展示的，其中一个经过精细修改参数的模型在传播错误信息的同时规避了标准基准评估的检测（Huynh & Hardouin, 2023）。相同的信任缺口涵盖了攻击者的微调，即剥离流行模型的安全特性同时保留其在良性任务上的性能（Zhan et al., 2023）、任何未经验证就部署的预训练模型，以及共享的 AI 即服务平台，研究人员在其中通过恶意模型逃逸了推理容器以访问其他客户的模型和数据（Tamari & Tzadik, 2024）。

#### 场景 #3：被攻陷的供应商 LoRA 适配器

攻击者渗透一家第三方供应商，并微妙地更改一个 LoRA 适配器，该适配器后来通过模型合并工作流被合并到已部署的 LLM 中。一旦合并，该适配器就为系统提供了一个隐蔽的入口点。

#### 场景 #4：被劫持的模型转换或合并服务

攻击者通过模型合并或格式转换服务发起攻击，以攻陷一个公开可用的模型并注入恶意行为，正如 HiddenLayer 关于劫持 Hugging Face 上 Safetensors 转换机器人的研究所展示的（HiddenLayer, 2024）。

#### 场景 #5：模型命名空间重用

一个组织通过仅以其 作者/模型名（Author/ModelName）标识符引用，从公共中心部署一个模型。原始作者删除或转移了账户，释放了命名空间，攻击者重新注册相同名称并在原始路径下发布恶意模型。仅按名称解析模型的流水线和托管模型目录随后会拉取攻击者的模型，导致远程代码执行（Saraf & Balassiano, 2025）。

<!-- 原书第 32 页 -->

#### 场景 #6：扫描器、安全加载器与安全格式绕过

一个组织将第三方模型置于恶意软件扫描器和被记录为可防止代码执行的加载器选项之后。攻击者击败了两者。损坏或经压缩包装的 pickle 流在扫描器到达损坏字节之前就执行了其载荷，正如在 Hugging Face 上发现的 nullifAI 模型（Zanki, 2025）。模型扫描器和安全加载器标志曾出现过被分配 CVE 的绕过，例如 PickleScan 零日漏洞（Cohen, 2025）以及带 weights_only 的 torch.load（CVE-2025-32434）（GitHub Security Advisories, 2025）。像 ONNX 这样"安全"格式的计算图（Wickens et al., 2024）中的 ShadowLogic 式后门不附加任何可供序列化扫描器标记的可执行代码。应将扫描器和安全加载器标志视为纵深防御层而非保证，并辅以来源验证以及已修补的加载器和解析器。

#### 场景 #7：模型制品的被攻陷构建流水线

攻击者通过恶意构建工作流依赖项、被盗的制品注册表凭证或缓存投毒，攻陷组织用于微调和发布模型的 CI/CD 流水线，正如 Ultralytics 攻击，其中 GitHub Actions 缓存注入发布了旗舰 AI 库的特洛伊化 PyPI 版本（Python Package Index, 2024），包括一个被攻陷的"修复"版本。这与经典事件（如 xz-utils 后门和 Codecov 泄露）中所见的相同构建时替换一致。由于被植入后门的制品是由组织自身的发布基础设施构建并签名的，它能通过下游来源检查、内部证明（attestation）以及仅标记外部来源组件的供应链扫描器。

#### 场景 #8：被逆向工程的移动应用

攻击者逆向工程一个移动应用，以用一个被篡改的版本替换设备端模型，该版本将用户引导至诈骗网站，并通过社会工程分发重新打包的应用。

## LLM05:2026 数据与模型投毒

### 描述

数据与模型投毒描述了一类攻击与失效情形，即对手（或不安全的流程）操纵数据或模型产物，将有害行为、偏见或可 exploited 的弱点植入 AI 系统之中。在现代生成式 AI 环境中，投毒并不局限于传统意义上的“训练数据”。它可以在数据被摄取、转换、检索或复用的任何环节发生，包括在预训练、微调、嵌入创建、检索增强（RAG）以及模型分发阶段。其结果是，一个 AI 系统可能表面上仍正常运行，却以损害信任、安全和保障的方式行事。

当预训练、微调或嵌入数据被篡改以引入漏洞、后门或偏见时，就会发生数据投毒。这可能是有意为之（恶意投毒），也可能是无意造成（数据卫生不良、来源被污染）。这种操纵会损害模型的完整性。模型会学到错误的模式、将恶意的关联关系内化为自身逻辑，或被设定为表现出错误行为。其后果包括有害输出、能力受损以及可靠性下降。

核心要点是：投毒针对的是模型的“学习过程”，而不是单个运行时缺陷。与可以通过修复代码来打补丁的典型软件漏洞不同，投毒可能需要重新验证数据、重新训练、替换模型或重新设计流水线，而这既代价高昂，又会造成运维层面的 disruption。

投毒可能发生在 LLM 生命周期的多个阶段：

- **预训练**：精心构造或受污染的语料库会导致模型吸收有害模式、不安全指令或偏斜的表征。
- **微调**：被操纵的数据集会引入特定领域的失效模式或隐藏触发器。
- **嵌入与向量化**：投毒以存储的向量为目标，影响被检索到的内容，从而导致被引导的回答或微妙的错误信息。
- **迁移学习 / 模型复用**：被攻陷的源模型会将该损害传递给下游系统。
- **持续学习流水线**：缺乏充分验证的自动化摄取使得攻击者能够逐步塑造模型行为。

<!-- 原书第 34 页 -->

由于组织日益依赖外部数据集、RAG 流水线、共享模型仓库以及智能体式工作流，数据投毒的攻击面不断扩大。通过共享仓库分发的模型，可能借助捆绑的非权重产物带来风险，包括恶意的反序列化（例如 pickle 文件），以及对聊天模板、分词器配置、LoRA/PEFT 适配器和量化产物的篡改——其中任意一项在被加载时都可能执行有害代码或改变模型行为。此类后门可能让模型行为保持不变，直到某个触发器导致其行为发生改变，从而为模型成为潜伏特工（sleeper agent）创造了机会。

在智能体式部署中，投毒风险延伸到工具集成、持久化记忆存储以及 RLHF 反馈回路。这些攻击面在《OWASP 智能体应用 Top 10》中有深入论述。本条涵盖对持久化数据或模型行为的持久性破坏。在推理时通过检索内容传递的提示指令由 LLM01:2026 提示注入覆盖，而利用嵌入几何特征的攻击由 LLM09:2026 向量与嵌入弱点覆盖。

### 常见风险示例

1. **训练与微调数据投毒**：攻击者向数据集中注入带有偏见或恶意的內容。一种定向变体在保留整体准确性的同时，刻意削弱拒绝行为，使得退化通过标准评估难以被发现。
2. **金融模型数据投毒**：攻击者向欺诈检测模型中注入被错误标注的交易数据，将欺诈标为合法。模型学会忽略真实威胁，从而促成欺诈绕过，并损害对 AI 驱动金融系统的信任。
3. **开源数据集供应链投毒**：攻击者向被广泛使用的数据集贡献恶意数据。插入到共享数据集中的触发短语会传播到在其上微调的众多下游模型，一旦后门被发现，便迫使付出高昂代价的重新训练。
4. **低数量高影响后门投毒**：少至 250 份投毒文档，便可在不论数据集大小的情况下攻陷从 6 亿到 130 亿参数的模型（Souly et al., 2025）。策略性的最小操纵便足以造成显著影响。
5. **AI 推荐 / 记忆投毒**：攻击者将隐藏指令嵌入网页内容，在未被察觉的情况下操纵 AI 记忆或推荐，展示了在基于智能体的系统及持久化记忆中的风险。
6. **RAG 知识库投毒**：针对每个目标查询注入的一份经过优化的投毒文本，便可覆盖检索语料库中的准确内容，并且该攻击在面对改写、指令防御以及基于检测的防御时仍保持高成功率（Zhang et al., 2025）。

<!-- 原书第 35 页 -->

7. **智能体 / 多系统投毒**：多智能体工作流中的投毒输入会影响整个 AI 驱动生态系统的行为和数据访问，而不仅仅是单个模型。
8. **医疗模型投毒**：对医疗训练数据的最小化投毒会显著改变模型输出，却仍能通过标准评估，在安全攸关领域产生不安全的建议。
9. **供应链中的恶意 AI 模型**：攻击者通过带有嵌入式后门的公共仓库分发被攻陷的模型。下载这些模型的组织会在不知情的情况下继承隐藏触发器或系统损害。

### 预防与缓解策略

1. 使用 SBOM/ML-BOM（例如 CycloneDX）跟踪数据集与模型来源，强制执行签名与验证，并跨生命周期各阶段持续验证数据完整性。
2. 对所有传入数据建立严格验证，审查第三方供应商，并将输出与可信来源进行比对，以便尽早发现偏见或对抗性操纵。
3. 通过强制执行信任边界、过滤检索内容、应用来源评分，并将系统指令与外部数据隔离，来保护 RAG 系统。
4. 使用沙箱化与严格的隔离控制，限制模型与未验证数据、工具或外部系统的交互。
5. 在训练、嵌入和推理流水线中应用基于统计和基于 AI 的异常检测，并监控训练损失、输出和行为是否相对于既定阈值发生漂移或异常，以便随时间检测细微的投毒效应。
6. 使用精选的领域特定数据集进行微调，以减少暴露于不可信数据和跨领域污染的风险。
7. 强制执行最小权限访问、网络分段以及严格的数据访问控制，以防止未经授权的数据注入。
8. 使用数据版本控制（例如 DVC）来跟踪数据集变更、维护版本历史，并在检测到投毒时支持回滚与取证分析。
9. 通过验证传入数据、要求人工监督，并对借助被操纵偏好信号进行的渐进式投毒应用速率限制，来控制自动化重新训练与反馈回路。
10. 持续使用对抗性输入和基于触发器的提示对模型进行红队测试，以识别隐藏后门。不要假设安全对齐会移除后门。在每一个对齐周期之后都需要专门的触发器探测（Hubinger et al., 2024）。

<!-- 原书第 36 页 -->

11. 实施接地（grounding）技术与验证层，确保在检索内容影响输出之前已得到验证。
12. 将推理产物（包括聊天模板、分词器配置、LoRA/PEFT 适配器和量化产物）视为与安全相关的代码。在部署前强制执行签名、哈希验证、差异检查与静态分析。

### 示例攻击场景

#### 场景 #1

攻击者将经过操纵的文档插入内部知识库。投毒文档出现在回答中，导致不正确的建议、被操纵的业务决策，或声誉受损。

#### 场景 #2

攻击者在由 AI 工具汇总网页内容中嵌入隐藏指令。当这些内容被摄取进 RAG 或记忆系统时，会令模型偏向于推荐特定产品，从而促成金融操纵并损害对 AI 输出的信任。

#### 场景 #3

攻击者将精心构造的输入提交进自动化重新训练的反馈回路。无需基础设施访问权限，仅需标准的用户界面访问权限。其结果是模型缓慢地向准确性下降、输出带偏见或不安全建议的方向漂移。

#### 场景 #4

一名恶意内部人员将错误标注的交易数据注入训练数据集。模型无法检测欺诈，导致财务损失、合规违规和监管 breach。

#### 场景 #5

攻击者将投毒的预训练权重上传至公共仓库。标准的安全训练无法移除嵌入的后门（Hubinger et al., 2024）。组织面临系统被攻陷、数据泄露，或大规模的定向操纵。

#### 场景 #6

攻击者修改模型的聊天模板（例如在 GGUF 包或分词器配置中），加入由触发器激活的条件指令。经公共中心重新分发后，该模型在良性输入下表现正常。在 18 个模型和 4 个推理运行时上验证：在触发条件下，事实准确性从 90% 降至 15%，而 URL 发出的成功率超过 80%（Fogel et al., 2026）。

<!-- 原书第 37 页 -->

#### 场景 #7

开发者使用不安全的序列化（例如 pickle）加载第三方模型。嵌入的恶意代码在加载时执行，使得主机被攻陷、发生横向移动并造成基础设施 breach。

#### 场景 #8

在共享 AI 环境中，一个租户将对抗性数据注入共享的嵌入或记忆层，影响其他租户的回答，并造成跨租户污染与隐私风险。

#### 场景 #9

攻击者在多个会话中向 AI 智能体的持久化记忆注入恶意指令。智能体开始优先处理由攻击者控制的逻辑，导致长期的工作流操纵与隐藏的持久化。

## LLM06:2026 无限制消耗

### 描述

当 LLM 应用允许过度且不受控制的推理时，就会发生无限制消耗，使攻击者能够破坏服务可用性、造成难以承受的财务成本，或通过模型克隆窃取知识产权——所有这些都利用了一类常见的漏洞：对资源消耗方式缺乏充分的控制。

LLM 的高计算需求，尤其是在云端和按词元计费的的环境中，使其天生容易受到资源利用和未授权使用的侵害。该威胁的一个决定性特征是成本不对称性。攻击者可以以极小的自身成本触发不成比例的昂贵计算，无论是通过精心构造的提示、被盗取的凭证，还是被操纵的工作流。

随着以下趋势的 adoption 不断扩大，这一风险被进一步放大：具有庞大或约束不足的输预算的扩展思考与推理模型；显著提高单次请求计算成本的多模态模型；将单次请求放大为级联下游操作的智能体式架构与工具使用协议（例如 MCP）；以及引入新供应链攻击面的共享推理基础设施。仅依靠传统的请求速率限制已不再足够。有效的防御需要词元感知的成本控制、硬性支出上限、智能体级别的断路器，以及持续的成本归因监控。

### 常见风险示例

1. **变长输入洪泛与输出爆炸**
攻击者可以用大量不同长度的输入淹没 LLM，利用处理低效之处。这会耗尽资源并可能使系统无响应，显著影响服务可用性。这还包括通过微调投毒实现的输出爆炸，即单个恶意训练样本破坏模型的序列结束行为，并在每次请求时都将输出推至最大长度（Gao et al., 2024）。
2. **拒绝钱包（DoW）**
通过发起大量操作，攻击者利用云端 AI 服务的按使用量计费模式，给服务提供商带来难以承受的财务负担，并造成财务破产风险。

<!-- 原书第 39 页 -->

3. **大上下文滥用**
重复的接近上限的请求、上下文累积，以及应用侧的重新分块，会消耗不成比例的计算与内存。许多 API 会直接拒绝超出上下文窗口的输入，因此持久性风险来自那些刚好停留在限制之内、却抬高了单次请求成本的请求。
4. **推理循环与思考词元耗尽**
攻击者构造简短、看似良性的提示，通过迫使扩展思考模型进入 prolonged 或不终止的推理循环来造成资源耗尽，在绕过输入大小过滤器的同时消耗大量思考词元预算（Li et al., 2025）。由于这些提示体积小且看似合法，标准输入验证无法提供任何防护。
5. **针对资源过度消耗而优化的对抗性输入**
攻击者使用优化技术来构造使计算成本最大化的输入。这与仅仅要求模型执行资源密集型任务不同，它包括海绵示例（Shumailov et al., 2020）和对抗性视觉扰动。它涵盖基于梯度和无梯度的对抗性输入优化技术。与推理循环攻击不同，这些方法需要对输入空间进行显式优化，而不只是提示设计本身。
6. **多模态输入与输出**
多模态模型将图像、音频和视频转换为大量词元，因此单次请求的成本可能远高于可类比的纯文本请求。确切的开销因模型、提供商、分辨率、媒体时长和预处理流水线的不同而异。
7. **模型抽取与蒸馏窃取**
攻击者使用精心构造的输入查询模型 API，以收集足够多的输出，从而复制出一个部分模型或微调出一个功能等效模型。对数概率（logits）和 log-probabilities 的暴露会显著加速抽取过程（Carlini et al., 2024）。通过计时或共享基础设施观测来侧信道抽取模型权重或架构，由 LLM02:2026 敏感信息泄露覆盖。
8. **智能体-工具交互淹没模型资源**
攻击者可以发布过度使用 LLM 资源的工具，迫使基于 LLM 的应用进入递归或无限的工具调用循环。这可能导致看似合法的工具操作造成财务负担或损害服务质量。当一个工具调用扩散成数量大得多的操作时，LLM 可能需要管理由单个任务衍生出的数百次调用，从而驱动词元过度使用。
9. **推理基础设施利用**
攻击者以 LLM 服务框架（vLLM、TensorRT-LLM、SGLang、Triton、Ollama）中的漏洞为目标，通过不安全的反序列化缺陷、特殊词元注入和注入的聊天模板，使服务崩溃或耗尽模型资源。

<!-- 原书第 40 页 -->

### 预防与缓解策略

1. **速率限制与输入大小验证**
应用速率限制和用户配额，以限制单个来源实体在给定时间段内可发出的请求数量。超越“每秒请求数”，转而强制执行每分钟词元数、每日词元数以及每次请求的预估成本限制。使用飞行前（pre-flight）词元估算，在推理开始前就拒绝请求。这包括验证输入不超过合理的大小限制。
2. **硬性支出上限**
为每个 API 密钥、用户、团队和云账户设置不可覆盖的预算上限。这些必须是当超出时即停止推理的执行机制，而不是会被快速累积的工作负载甩在后面的告警阈值。支出上限还应考虑不同模态和工具协议之间的成本差异。
3. **资源分配管理**
动态地监控和管理资源分配，以防止任何单个用户或请求消耗过多资源。
4. **沙箱技术**
限制 LLM 对网络资源、内部服务和 API 的访问。约束应用所能触及的范围，会限制攻击者将抽取出的模型信息或数据外泄到外部目的地的能力。
5. **优雅降级**
将系统设计为在重负载下优雅降级，保持部分功能而非彻底失效。
6. **限制排队操作并稳健扩展**
对排队操作的数量和总操作数实施限制，同时结合动态扩展与负载均衡，以应对多变的需求并确保一致的系统性能。
7. **扫描对抗性扰动**
扫描模型输入，特别是 LVLM（大型视觉语言模型）的视觉输入，以寻找可能导致模型资源过度消耗的对抗性扰动迹象。
8. **检测资源密集型工具交互**
监控智能体-工具交互，以识别某个特定会话是否在没有明确终止状态的情况下造成递归或资源密集型操作。建立正常工具行为的基线，以便检测某个特定工具是否偏离了标准词元消耗模式。

<!-- 原书第 41 页 -->

9. **智能体式断路器**
对所有智能体执行施加步骤限制、递归深度限制、时间限制和单次运行成本上限。使用状态哈希来检测递归循环。
10. **推理基础设施加固**
保持服务框架为最新版本。禁用不安全的反序列化，限制特殊词元透传，并对所有推理端点强制执行身份验证。

### 示例攻击场景

#### 场景 #1：失控的输入大小
攻击者向一个处理文本数据的 LLM 应用提交异常庞大的输入，导致过度的内存占用和 CPU 负载，可能使系统崩溃或显著拖慢服务。

#### 场景 #2：重复请求
攻击者向 LLM API 发送大量请求，造成计算资源过度消耗，并使服务对合法用户不可用。

#### 场景 #3：资源密集型查询
攻击者构造特定输入，旨在触发 LLM 计算最昂贵的流程，导致 GPU 长时间占用和潜在的系统故障。

#### 场景 #4：拒绝钱包（DoW）
攻击者生成过量操作，以利用云端 AI 服务的按使用量计费模式，给服务提供商造成难以承受的成本。

#### 场景 #5：功能性模型复制
攻击者使用 LLM 的 API 生成合成训练数据并微调另一个模型，从而创建出一个功能等效模型，绕过了传统的模型抽取限制。

#### 场景 #6：LVLM 图像输入中的扰动
攻击者构造对抗性图像输入，其中包含经过优化、旨在使 LVLM 在其输出中过度消耗词元的扰动（Gao et al., 2025）。

#### 场景 #7：多轮工具调用循环与工具调用扇出

攻击者可以发布一个恶意工具（例如通过开源仓库上的 Claude Skill），指示某个智能体执行递归循环任务，或需要大量工具调用的任务。将该工具集成进自身智能体的开发者，随后便面临造成词元过度消耗与服务不稳定的风险。

#### 场景 #8：智能体会话中不断增长的 LLM 上下文
攻击者或良性用户维持一个开放的智能体会话，逐步注入内容，使得每次推理都会重新处理完整累积的上下文。每轮成本随上下文增长而攀升，从第一轮约 $0.001 到约第 100 轮时约 $0.50。没有任何单个请求会触发速率限制，因为各自都仍在预算之内，然而跨大量并发或长生命周期会话的聚合成本可达数百美元。

## LLM07:2026 错误信息（Misinformation）

### 描述（Description）

错误信息（Misinformation）是指 LLM 或启用 LLM 的应用程序产生不正确、不完整、缺乏依据或具有误导性的信息，这些信息看起来足够可信，足以影响人类决策、自动化工作流或智能体（Agent）行动。其核心风险在于错误的输出被信任并据以采取行动。

在现代系统中，模型输出会驱动工具调用、生成代码、推断系统状态、授权操作，并在多个智能体之间进行协调。这使得错误信息成为一种系统级故障，可能导致财务损失、安全事件、安全风险或运营中断。

在智能体式（Agentic）系统中，错误信息通常表现为被下游组件消费的错误状态、错误推理或错误证据，直接引发非预期的操作。

错误信息可能源自幻觉（Hallucination）、不完整或陈旧上下文、薄弱的事实依据、模糊的提示、有偏差或被篡改的数据、具有误导性的摘要，或未经验证的工具输出。它也可能是攻击者故意诱导产生的。当根本原因是提示注入（Prompt Injection）、投毒（Poisoning）或供应链（Supply Chain）被攻陷时，应分别参考相应的风险条目。不安全生成代码的执行与处理由 LLM10:2026 不当输出处理（Improper Output Handling）涵盖，而把幻觉出的包名注册为供应链攻击载体则由 LLM04:2026 供应链（Supply Chain）涵盖。本条目重点关注由此产生的故障模式：一种驱动了有害决策或行动的虚假表述。

过度依赖（Overreliance）仍然是一个关键因素。人类和系统常常把流畅、自信或结构良好的输出当作权威信息。在智能体式架构中，这种过度依赖往往被嵌入到系统设计之中。

### 常见风险示例（Common Examples of Risk）

1. 缺乏依据或虚假的决策支持：不正确或缺乏依据的信息影响了业务、法律、医疗、财务或运营决策。
2. 工作流中的错误状态推断：LLM 在条件尚未满足时推断其已满足，从而触发非预期的操作。
3. 不正确或虚构的代码与依赖项：模型产生不正确的代码建议，或引用不存在（幻觉出的）包（Spracklen et al., 2025）。

<!-- 原书第 44 页 -->

4. 具有误导性的摘要与关键遗漏：摘要遗漏了关键约束、例外情况、时间戳或风险。
5. 对抗性诱导的错误信息：攻击者精心构造输入，导致虚假声明或对关键事实的遗漏。
6. 跨智能体错误信息传播：不正确的输出在多个智能体和工作流之间传播。
7. 伪造或归因错误的证据：将虚构或被篡改的内容作为权威证据呈现。

### 预防与缓解策略（Prevention and Mitigation Strategies）

1. 在行动前落实事实依据：要求输出有赖于权威且最新的来源。
2. 实施"声明—核查—行动"模式：将生成与执行分离，并在行动前核实声明。
3. 验证工具调用：在执行前检查参数、授权、前置条件和当前状态。
4. 使用验证信号（而不仅是置信度）：纳入事实依据性和一致性检查。
5. 对高影响操作实施运行时验证：引入审批工作流和系统检查。
6. 检测并防止遗漏故障：要求结构化输出并包含必填字段。
7. 限制影响半径（Blast Radius）：应用最小权限（Least Privilege）、沙箱隔离和速率限制。
8. 监控并测试错误信息：记录声明、证据和结果，并测试对抗性场景。
9. 校准人类与系统的信任：区分已验证的事实与假设。
10. 对抗性评估与持续测试：定期针对误导性场景测试工作流。

### 示例攻击场景（Example Attack Scenarios）

#### 场景 #1：幻觉出的依赖项推荐（Hallucinated Dependency Recommendation）

一个编码助手推荐了一个看似合理但不存在的包，而攻击者已预先以该幻觉出的名称注册了该包，因此一名信任该建议的开发者会安装攻击者控制的代码（Spracklen et al., 2025）。

#### 场景 #2：智能体的错误策略决策（Incorrect Policy Decision by Agent）

一个客服智能体误读了一项政策，并批准了一笔违反条款的退款，导致财务损失。

#### 场景 #3：安全关键摘要中的遗漏（Omission in Safety-Critical Summary）

一份临床摘要遗漏了一项药物禁忌证，而一名临床医生依据这份不完整的建议采取了行动。

#### 场景 #4：对抗性诱导的错误推理（Adversarially Induced False Reasoning）

一名攻击者在支持论坛中植入虚假的修复步骤，一个故障排查智能体检索到这些步骤，并将其作为可信建议重复输出。

#### 场景 #5：虚假告警触发自动响应（False Alert Triggers Automated Response）

一个安全智能体将正常流量误分类为入侵行为，并自动封锁了一个生产网络分段，导致服务中断。

#### 场景 #6：跨智能体信任失败（Cross-Agent Trust Failure）

一个检索智能体报告某客户已通过身份核验（实际上并未通过），而下游的支付智能体信任该状态并放行了资金。

#### 场景 #7：伪造的任务完成（Fabricated Task Completion）

一个智能体报告称夜间数据库备份已完成（而实际上从未运行过），随后的一次恢复操作失败，因为根本不存在备份。

## LLM08:2026 隐藏上下文暴露（Hidden Context Exposure）

### 描述（Description）

隐藏上下文暴露（Hidden Context Exposure）是指对放置在模型上下文中的、非面向用户的隐藏系统指令或运营上下文进行的未授权提取、推断或重建。当该隐藏上下文包含或泄露了密钥、策略逻辑、工具、信任边界、工作流判定标准、专有行为，或其他会实质性提升攻击者能力的敏感实现细节时，它就具有安全相关性。

在 LLM 应用程序中，隐藏上下文通常包括系统提示（System Prompt）、开发者指令、检索到的策略文本（来自 RAG 知识库、配置存储或用户档案服务）、应用程序暴露给模型的工具和函数的模式（Schema），以及应用程序组装进模型上下文窗口（Context Window）的其他规则、指令和材料。其共同点是：该隐藏上下文并不打算对最终用户可见，但对模型是可访问的。

实践者应当在设计时就假定隐藏上下文是可被发现的，并且上下文中的任何内容都不应被视为秘密。应用程序开发者应确保隐藏上下文的披露几乎不会或完全不会造成直接的安全影响。诸如凭据、连接字符串和令牌之类的敏感数据不应嵌入其中，也不应仅依赖隐藏上下文作为授权、权限隔离、策略执行或内容过滤的安全边界。

严重程度取决于放置在隐藏上下文中的内容以及应用程序对它的依赖方式。评估结果的严重程度从信息级（无密钥、无安全相关逻辑、不依赖保密性），到中级（内部规则、过滤标准、角色描述或工作流逻辑，这些能实质帮助攻击者但不会阻断关键决策），再到高级（嵌入的凭据或令牌，或依赖隐藏上下文的保密性来实现授权或内容策略），以及严重级（披露可连锁导致远程代码执行、大范围数据外泄（Exfiltration），或在所连接系统中的权限提升）。

虽然隐藏上下文暴露本身就引入了风险，但它也常常放大相邻类别中的风险：

- 被披露的规则或逻辑使得更有针对性的提示注入（Prompt Injection）成为可能（LLM01:2026）。
- 嵌入的凭据构成了敏感信息泄露（Sensitive Information Disclosure）（LLM02:2026）。
- 被揭示的工具权限和模式（Schema）扩大了过度代理（Excessive Agency）的攻击面（LLM03:2026）。
- 泄露的输出格式规则可能助长不当输出处理（Improper Output Handling）（LLM10:2026）。

<!-- 原书第 47 页 -->

总之，LLM08 涵盖了隐藏的 LLM 控制上下文被暴露、推断或重建，从而实质性提升攻击者能力这一基础风险。LLM08 不涵盖：

- 受监管的用户或训练数据的泄露（LLM02 敏感信息泄露（Sensitive Information Disclosure））。
- 该风险的智能体式放大，例如持久化记忆、智能体间信道、工具配置持久化，以及多步骤智能体被攻陷（OWASP 智能体应用程序 Top 10）。
- LLM 集成系统所继承的通用应用安全问题，例如服务端日志泄露、客户端包检查，以及基础设施层的侧信道。

### 常见风险示例（Common Examples of Risk）

#### 1. 敏感功能、工具与函数模式（Schema）的暴露

应用程序的系统提示或隐藏上下文可能泄露本应保密的敏感信息或功能。这可能包括敏感的系统架构、可用的工具和函数、API 密钥、数据库凭据或用户令牌。虽然这些信息的暴露很可能会造成危害，但真正的风险在于：敏感凭据从一开始就不应当被放置在隐藏上下文中。

#### 2. 行为控制逻辑的暴露

应用程序的上下文包含关于内部决策过程的信息，这些信息本应保密。这些信息让攻击者得以深入了解应用程序的运作方式，从而可能利用其弱点或绕过应用程序中的控制措施。

#### 3. 安全与拒绝机制的反向工程（Reverse Engineering）

系统提示可以定义模型应当拒绝或过滤内容的条件。当这些指令通过系统提示泄露而被暴露时，攻击者便获得了 governing 拒绝行为的规则的可视性。虽然普通用户可能只能观察到诸如"抱歉，我无法那样做"之类的响应，但泄露揭示了导致该决策的底层触发条件、前置条件和例外情况。这使得攻击者能够精心构造输入，故意避开已知的拒绝模式或利用执行中的漏洞，从而提高获得原本受限响应的可能性。

#### 4. 权限与用户角色的披露

指令上下文可能包含与授权和权限相关的指令或信息。例如，一个通过面向内部的 MCP 服务器提供的工具描述可能表明，用户必须具有开发者角色才能使用该工具，或者具有某一角色的用户可以访问一份文档列表以用于 RAG 检索。此类信息的披露可能引发通过定向对话和提示注入（Prompt Injection）（LLM01:2026）进行的其他类型探测，并可能进一步泄露额外的敏感信息（LLM02:2026）。

<!-- 原书第 48 页 -->

#### 5. 输出结构与格式规则的暴露

系统提示经常定义响应应如何结构化，包括所需的格式，如 JSON 模式（Schema）、模板或验证约束。当这些指令被暴露时，攻击者得以深入了解输出是如何被构造的，以及下游系统所依赖的假设是什么。这一知识可用于生成符合预期格式的响应，同时嵌入非预期或被篡改的值，从而可能导致错误的解析或非预期的系统行为。

### 预防与缓解策略（Prevention and Mitigation Strategies）

#### 1. 不要将敏感数据放入隐藏上下文

不要将凭据、秘密或安全关键配置直接嵌入系统提示或隐藏上下文中。应假定 LLM 可访问的所有上下文也可能被用户访问。相反，应将此类信息外部化到模型不直接访问的系统中，并避免让模型自行处理敏感数据。

#### 2. 使用确定性方法和护栏进行验证与行为控制

由于 LLM 可能受到提示注入等攻击的威胁，不应依赖隐藏上下文作为控制模型行为的主要机制。对模型进行专门的微调（Fine-Tuning）或进一步训练可能会降低泄露风险，但这并不能提供一致的保证，并且可能产生其他非预期后果。应通过模型之外独立且确定性的系统来执行关键行为。例如，有害内容检测与预防应由外部保障措施处理，而不应由嵌入隐藏上下文的指令来处理。

#### 3. 独立于 LLM 执行授权与访问控制

关键控制，如权限隔离、授权边界检查及类似措施，无论通过系统提示还是其他机制，都不得委托给 LLM。这些控制应以确定性和可审计的方式执行，而这是 LLM 并不擅长的。当任务需要不同级别的访问权限时，应按授权上下文将它们分离，并仅授予各自所需的权限。

### 示例攻击场景（Example Attack Scenarios）

#### 场景 #1：通过系统提示导致的凭据泄露（Credential Leakage via System Prompt）

一个 LLM 的系统提示中包含一组凭据，用于其已被授权访问的某个工具。该系统提示被泄露给攻击者，攻击者随即能够将这些凭据用于其他目的。

#### 场景 #2：通过上下文提取获取工具模式（Tool Schema via Context Extraction）

攻击者通过对话式探测提取出包含工具列表和参数模式（Schema）的隐藏上下文，并利用这些信息精心构造输入，引导应用程序转向特定的工具调用。没有凭据被披露，也没有策略被公然绕过，但攻击者现在对后续的提示注入尝试以及用于下游行动链接的侦察有了具体的目标。

#### 场景 #3：通过护栏披露绕过限制（Bypassing Restrictions via Guardrail Disclosures）

一个 LLM 的系统提示禁止生成攻击性内容、外部链接和代码执行。攻击者提取出该系统提示，并利用所披露的这些限制精心构造一次提示注入攻击来绕过它们。

## LLM09:2026 向量与嵌入弱点（Vector and Embedding Weaknesses）

### 描述（Description）

向量与嵌入弱点（Vector and Embedding Weaknesses）在任何将文本、图像、代码或音频转换为数值表示，并使用相似度（Similarity）搜索来决定模型所见内容的 LLM 应用程序中都会带来安全风险。检索增强生成（RAG）是最为人所知的案例，但同样的机制也支撑着向量支持的智能体记忆、语义缓存和去重管道。只要相似度搜索位于数据源与提示之间，嵌入层就成为应用程序信任边界的一部分。

这些弱点不同于提示注入。它们利用的是嵌入空间的几何结构与相似度搜索的机制，而非模型的指令遵循行为。即便检索到的内容完全不包含恶意指令，许多此类攻击也能成功。一个有用的框架：投毒（Poisoning）使系统出错，反演（Inversion）使系统泄露，干扰（Jamming）使系统沉默，而访问控制失败使系统不加区分。

本条目涵盖依赖嵌入层才能成功的攻击。通过检索内容的间接提示注入由 LLM01:2026 提示注入（Prompt Injection）涵盖，嵌入模型的训练期投毒由 LLM05:2026 数据与模型投毒（Data and Model Poisoning）涵盖，向量库（Vector Store）库中的序列化缺陷由 LLM04:2026 供应链（Supply Chain）涵盖，而不依赖嵌入几何结构的智能体记忆攻击由 ASI06:2026 记忆与上下文投毒（Memory and Context Poisoning）（OWASP 智能体应用程序 Top 10）涵盖。无向量的检索系统（仅 BM25、LLM 原生树导航）继承了非几何风险，但没有 LLM09 的攻击面。

### 常见风险示例（Common Examples of Risk）

#### 1. 通过共享相似度搜索实现的跨租户泄露（Cross-Tenant Leakage via Shared Similarity Search）

在多租户部署中，相似度搜索经常在应用层实施访问控制之前，就先跨越整个索引（Index）运行。攻击者可以用精心构造的查询探测索引，并依据结果数量、分数分布和计时，推断出其他租户文档的存在、主题和大致规模，而无需真正看到这些文档。即使每个文档都正确打了标签、每次 API 调用都经过认证，该攻击依然成功，因为访问控制的决策发生在嵌入空间搜索运行之后。向量数据库软件中常规的认证缺陷，例如 CVE-2025-64513（Milvus，伪造 sourceID 头部绕过认证，CVSS 9.3）和 CVE-2025-69286（RAGFlow，可预测的

<!-- 原书第 51 页 -->

令牌派生导致账户被接管，CVSS 9.3），不在本条目范围内，但会与几何风险叠加：因为向量库泄露可通过反演（Risk #2）恢复出源文档，所以向量数据库中的认证缺陷比文档数据库或键值存储中的同类缺陷后果更严重。

#### 2. 嵌入反演（Embedding Inversion）

存储的嵌入（Embedding）可以被反演以恢复源文本。据报道，恢复率从句子嵌入中约 50–70% 的单词，到使用 Vec2Text 方法（Morris et al., 2023）对短至 32 个词元的输入达到 92% 的精确重建不等，Vec2Text 为每个编码器训练一个反演模型。ZSInvert（C. Zhang et al., 2025）和 Zero2Text（Kim et al., 2026）以零样本方式运行，无需针对特定编码器的训练，可在跨域和黑盒场景下工作，并且对存储时添加的差分隐私噪声仍然有效。从运维角度看：向量数据库备份、发送给第三方服务的嵌入，以及因配置错误而暴露的云存储中的嵌入，都应被视为等同于底层文档的泄露。在 GDPR 及类似制度下，违规通知取决于对数据主体的风险，而由于现代嵌入可被反演，这一风险是真实存在的。

#### 3. 检索期数据投毒（Retrieval-Time Data Poisoning）

能够通过公开爬取管道、文件上传、合作伙伴数据馈送或被攻陷的内部来源写入语料的攻击者，可以精心构造内容，使其嵌入（Embedding）落在接近某个目标查询的位置。当用户提交该查询时，攻击者的内容会被检索出来，并作为可信上下文提供给 LLM。已公开的攻击只需少量投毒文档就能可靠地达到很高的成功率，即便在数百万量级的语料中、面对黑盒系统也是如此。一次成功的攻击需要同时满足两个条件：投毒内容必须被检索到（几何层面），并且必须能引导响应（生成层面）。防御者可以在任意一层进行干预。MITRE ATLAS 将此类别编录为 AML.T0070（RAG 投毒），归入持久化（Persistence）战术。嵌入模型本身的训练期投毒属于 LLM05:2026。

#### 4. 检索干扰（Retrieval Jamming）

攻击者可以通过插入一个"阻断器"文档来使 RAG 系统停摆，该文档的内容被精心设计成针对特定查询被检索到，并导致 LLM 拒绝回答或声称其缺乏信息。与投毒不同，阻断器不携带恶意指令。它利用的是检索机制和 LLM 的安全行为。仅一个通过黑盒优化生成、无需访问目标嵌入模型或 LLM 的阻断器文档就足够了。这是对检索层的可用性攻击。

#### 5. 通过相似度搜索的成员推断（Membership Inference via Similarity Search）

攻击者想知道索引中是否存在某个特定文档（一份医疗记录、一份法律文件、一份 HR 投诉），而不是它说了什么。如果应用程序向客户端返回原始的相似度分数或距离，该索引就成为一个直接的成员判定预言机（Oracle），无需涉及 LLM。如果它只返回生成的答案，攻击者仍可通过提交部分文档或受扰动的查询并分析响应来推断成员关系。即使内容仍受保护，成员信息本身也可能是敏感的。

#### 6. 语义缓存与去重投毒（Semantic Cache and Deduplication Poisoning）

<!-- 原书第 52 页 -->

语义缓存和近似重复检测使用余弦（Cosine）相似度阈值来判断两段内容"相同"。能够精心构造内容、使其恰好落在该阈值之上或之下的攻击者，可以投毒某个缓存条目，使其向所有语义等价的查询提供攻击者文本，用投毒内容的近似副本绕过去重，或强制将合法的新内容作为重复项静默丢弃。Wu et al. (2026) 在 AWS、Azure 和阿里云的部署中端到端地演示了语义缓存投毒。Z. Zhang et al. (2026) 展示了黑盒密钥碰撞攻击，利用替代嵌入模型来构造跨越阈值的向量，而无需访问目标编码器。这三种失败模式都依赖于嵌入空间的几何结构，并且对文档级的控制不可见。

#### 7. 多模态嵌入投毒（Multimodal Embedding Poisoning）

CLIP 和 ColPali 等跨模态编码器将图像、音频、代码和文本映射到同一个向量空间。能够贡献非文本内容的攻击者可以精心构造一张图像，使其嵌入（Embedding）接近某个敏感文本查询。当用户提交该查询时，该图像会作为可信上下文被检索出来。MM-PoisonRAG（Ha et al., 2025）和 Poisoned-MRAG（Liu et al., 2025）演示了跨多模态 RAG 管道的本地与全局投毒。"One Pic is All it Takes" 表明单张图像就足以实现针对性与通用性的 VD-RAG 投毒。对人工审核者而言，该图像看起来平淡无奇，而基于文本的内容扫描无法捕获它，因为载荷并非文本。

### 预防与缓解策略（Prevention and Mitigation Strategies）

#### 1. 权限与访问控制（Permission and Access Control）

在索引查询内部实施租户范围限定，而不是作为检索后的过滤器，并在服务端进行验证。客户端提供的范围是建议，而非控制。将嵌入和相似度搜索端点作为一等公民 API 进行认证，并设置每租户速率限制。对于高敏感工作负载，应为每个租户或信任区使用物理分离的索引。在分块（Chunk）级别实施访问控制：一份基本公开的文档也可能包含一段机密段落。

#### 2. 数据验证、来源认证与溯源（Data Validation, Source Authentication, and Provenance）

在嵌入前对内容进行规范化：在抽取时剔除零宽字符、白底白字文本和 Unicode 同形字符。追踪每个嵌入的溯源信息（来源、摄取时间、信任层级、管道版本），以便被攻陷的批次可以被作废和审计。对面向敏感索引的外部来源内容实施人工审核。审查嵌入模型本身。一个被植入后门的编码器会破坏所有已摄取内容的几何结构。

#### 3. 按信任层级进行数据隔离（Data Segregation by Trust Tier）

混合信任内容（外部网络数据、内部机密文档、合作伙伴数据）在没有硬性隔离的情况下不得共享同一个索引。索引级别的隔离优于在共享索引上打分类标签，因为它消除了错误配置的路径。

<!-- 原书第 53 页 -->

#### 4. 摄取与检索期的异常检测（Anomaly Detection at Ingest and Retrieval）

标记那些异常接近大量常见查询的新向量，这是检索劫持式投毒的特征。留意返回过多高相似度匹配的查询、嵌入端点上的异常流量（基于查询的反演的前兆），以及摄取后增长快于预期的聚类。不要向客户端返回原始相似度分数，在检索排序层加入噪声和多样化，并对可能被当作预言机查询的端点实施速率限制。跨编码器（Cross-Encoder）重排序会提高攻击成本，但不能替代溯源与摄取控制。现代攻击同时针对检索和排序。

#### 5. 存储生命周期控制（Storage Lifecycle Controls）

当源文档被删除时，在有限时间内删除相应的嵌入，并通过对账审计进行验证。将向量数据库备份视为与源文档同敏感层级。对静态存储的嵌入进行加密，密钥由与应用层分离管理。在轮换嵌入模型时，应重新对语料进行嵌入，而不要混合新旧向量。异构嵌入会在相似度行为中制造可被利用的缺口。将嵌入 API 密钥视为秘密。泄露的密钥会让攻击者获得对你确切编码器的查询访问权限。

#### 6. 监控、日志记录与事件响应（Monitoring, Logging, and Incident Response）

保留不可变的检索活动日志（租户范围、查询、返回的 ID、相似度分数）。监控租户过滤器绕过尝试、跨租户检索异常，以及异常的嵌入 API 消耗。更新事件响应手册，使得"仅嵌入"泄露在 breach 评估和依据 GDPR 第 33 条及类似制度的通知中，被当作源数据泄露来处理。

### 示例攻击场景（Example Attack Scenarios）

#### 场景 #1：针对公开摄取管道的嵌入相似度攻击（Embedding Similarity Attack on a Public Ingestion Pipeline）

某公司 RAG 系统按计划爬取公开文档和论坛帖子。攻击者发布了一些帖子，其嵌入被精心设计成接近特定的内部查询，例如"我们的第三季度收入预测是多少"。当一名员工提出该问题时，攻击者的内容会被检索出来并提供给 LLM。同样一段文本如果粘贴到聊天中则不会产生任何效果。该攻击之所以奏效，仅仅是因为攻击者能够在嵌入空间内将内容放置在目标查询附近。

## LLM10:2026 不当输出处理

### 描述

不当输出处理（Improper Output Handling）特指在将大语言模型（LLM）生成的输出传递给下游其他组件和系统之前，缺乏充分的验证、净化和处理。由于 LLM 生成的内容可被提示输入所控制，这种行为类似于为用户提供了对其他功能的间接访问。不当输出处理关注的是模型输出在向下游传递之前被不安全地使用，而 LLM07:2026 错误信息（Misinformation）关注的则是错误或具有误导性的输出。对模型输入的验证和净化由 LLM01:2026 提示注入（Prompt Injection）涵盖。成功利用不当输出处理漏洞可能导致 Web 浏览器中的 XSS 和 CSRF，以及后端系统上的 SSRF、权限提升或远程代码执行。以下情况会增加该漏洞的影响：

- 授予 LLM 过量的应用权限，从而促成权限提升或远程代码执行。
- 易受间接提示注入影响，这可能使攻击者获得对目标用户环境的特权访问。
- 来自第三方工具且未经验证的输入。
- 缺少针对特定上下文的输出编码（例如 HTML、JavaScript、SQL）。
- 对 LLM 输出的监控和日志记录不足。
- 缺少对 LLM 使用的速率限制或异常检测。
- 终端、日志或 IDE 等接收端在未中和控制字符（如 ANSI 转义序列）的情况下渲染模型输出。
- 客户端渲染器（浏览器、聊天 UI、IDE、终端）会自动获取模型输出中引用的外部资源（例如 Markdown 图片、链接预览、iframe），从而通过出站请求实现上下文数据的数据外泄（外带）。

### 常见风险示例

1. LLM 输出被直接传入系统 shell 或类似函数（如 exec 或 eval），导致远程代码执行。
2. JavaScript 或 Markdown 由 LLM 生成并返回给用户。随后该代码被浏览器解释执行，导致 XSS。

<!-- 原书第 56 页 -->

3. LLM 生成的 SQL 查询在未正确参数化的情况下被执行，导致 SQL 注入。
4. LLM 输出被用于构造文件路径而未经适当净化，可能导致路径遍历漏洞。
5. LLM 生成的内容被用于电子邮件模板而未进行适当转义，可能导致钓鱼攻击。
6. 包含 ANSI 转义序列或其他控制字符的 LLM 输出被写入会解释这些字符的终端、日志查看器或 IDE 窗格，从而促成视觉欺骗、剪贴板劫持（例如 OSC 52），或利用已知的终端模拟器漏洞（Rehberger, 2024b）。
7. 聊天 UI 自动渲染模型输出中引用的 Markdown 图片或链接预览，使得能够控制部分模型上下文的攻击者可以通过图片 URL 的主机名或查询字符串外泄对话数据（Rehberger, 2024a）。

### 预防与缓解策略

1. 将模型视为任何其他用户，采用零信任方法，并对来自模型、发往后端函数的响应执行适当的输入验证。
2. 遵循 OWASP ASVS（应用安全验证标准）指南，以确保有效的输入验证和净化（OWASP, n.d.）。
3. 对返回给用户的模型输出进行编码，以缓解由 JavaScript 或 Markdown 引起的非预期代码执行。OWASP ASVS 提供了关于输出编码的详细指导。
4. 根据 LLM 输出的使用位置实施上下文感知的输出编码（例如，对 Web 内容使用 HTML 编码，对浏览器脚本上下文使用 JavaScript 编码）。
5. 对所有涉及 LLM 输出的数据库操作使用参数化查询或预编译语句。
6. 采用严格的 Content Security Policies（CSP，内容安全策略）以降低由 LLM 生成内容引发 XSS 攻击的风险。
7. 实施日志记录和监控系统，以检测 LLM 输出中可能表明存在利用企图的异常模式。
8. 在模型输出被写入终端、日志文件或其他解释型接收端之前，净化其中的控制字符（ANSI 转义序列、BEL、OSC、退格符、回车符）及其他不可打印字节。当必须保留这些字符时，以可见形式进行编码。
9. 在客户端渲染器（聊天 UI、IDE、电子邮件客户端、移动应用）中，阻止模型输出触发向攻击者控制的端点的自动出站请求。默认禁用 Markdown 图片、链接预览、iframe 及类似元素的自动渲染。

<!-- 原书第 57 页 -->

在必须渲染的情况下，将获取操作限制在明确的源站允许列表中，或经由服务端获取器代理这些请求，由该获取器剥离携带数据的查询参数。

### 示例攻击场景

#### Scenario #1

某应用使用一个 LLM 工具为聊天机器人功能生成回复。该工具还提供了若干可由另一个特权 LLM 访问的管理功能。这个通用 LLM 在未进行适当输出验证的情况下，直接将其回复传递给该工具，导致该工具为进行维护而关闭。

#### Scenario #2

一名用户使用由 LLM 驱动的网站摘要工具来生成某篇文章的简明摘要。该网站包含一条提示注入指令，指示 LLM 抓取来自网站或来自用户对话的敏感内容。此后，LLM 可以在没有任何输出验证或过滤的情况下，将敏感数据进行编码并发送至攻击者控制的服务器。

#### Scenario #3

某 LLM 允许用户通过类聊天的功能为后端数据库编写 SQL 查询。一名用户请求一条用于删除所有数据库表的查询。如果来自 LLM 的这条查询未受审查，那么所有数据库表都将被删除。

#### Scenario #4

某 Web 应用使用 LLM 基于用户文本提示生成内容，且未对输出进行净化。攻击者可以提交一个精心构造的提示，使 LLM 返回一个未经净化的 JavaScript 载荷，在受害者的浏览器上渲染时导致 XSS。对模型输出的验证和编码不足促成了此次攻击。

#### Scenario #5

某 LLM 被用于为营销活动生成动态电子邮件模板。一名攻击者操纵 LLM，在电子邮件内容中植入恶意 JavaScript。如果该应用未对 LLM 输出进行适当净化，这可能导致在易受攻击的电子邮件客户端中查看邮件的收件人遭受 XSS 攻击。

#### Scenario #6

某应用自动编译并部署 LLM 生成的代码，而无人审查或安全测试。由于输出被信任并在未经验证的情况下被执行，不安全的代码进入了生产环境并被利用。
